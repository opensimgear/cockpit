# HID coverage and evidence matrix

This matrix defines the H0 requirements for #178. The current-support columns describe the
`crates/controller-input` implementation at commit `30af9948`. The [device corpus](../../tests/hid-device-captures/)
records the observations from the Windows host.

H0 must distinguish original bytes, parsed descriptor facts, OS-derived metadata, decoded samples and inferred application meaning. A backend that supplies only parsed elements cannot reconstruct an original report descriptor or establish the values of flags it omitted. Unknown, unavailable, unsupported and malformed are separate outcomes; none means zero, released, centered or safe to map.

## Standards and source boundaries

The class baseline here is [USB-IF HID 1.11](https://www.usb.org/sites/default/files/documents/hid1_11.pdf), particularly §§5.6, 5.10 and 6.2.2. Item families: Main, Global, Local; short and long encodings. Main data items: Input, Output, Feature; grouping: Collection/End Collection. Global metadata includes usage page, logical/physical bounds, unit/exponent, report size/count/ID and Push/Pop. Local metadata includes usages/ranges, designators, strings and Delimiter. Flags cover data/constant, array/variable, absolute/relative, wrap, nonlinear, preferred state, null and buffered bytes; Output/Feature additionally have volatility. Input's corresponding bit is reserved. Array fields carry selectors; variable fields represent individual values. Null is not ordinary zero; relative is not absolute position. These statements summarize class semantics, not present Cockpit support.

Usage names/types are a separate dictionary from class parsing. Use [USB-IF HID Usage Tables 1.7](https://www.usb.org/sites/default/files/hut1_7.pdf), especially §3 and the relevant usage-page section. Keep numeric page/usage when names are absent. Usage type, collection context and flags constrain interpretation; a familiar name alone does not authorize axis/button conversion. The [USB-IF publication page](https://www.usb.org/document-library/hid-usage-tables-17) currently lists 1.7; the former 1.6 landing URL redirects there. Pin the actual dictionary revision in fixture evidence. This does not change the class baseline to a newer HID version or assert support for all table entries.

Current implementation references used below:

- **W**: [`windows.rs`](../../crates/controller-input/src/windows.rs), `eligible`, `device`, `parse_caps`, `input`; [`windows/worker.rs`](../../crates/controller-input/src/windows/worker.rs).
- **L**: [`linux.rs`](../../crates/controller-input/src/linux.rs), `controls`, `Frames`, `definition`, `LinuxInput`; this is evdev, not hidraw.
- **M**: [`macos.rs`](../../crates/controller-input/src/macos.rs), `Element`, `controls`, `NativeHandle::elements`, `Queue::drain`, `MacInput::baseline`; [`macos/provider.rs`](../../crates/controller-input/src/macos/provider.rs).
- **C**: [`registry/model.rs`](../../crates/controller-input/src/registry/model.rs), `Control`, `Control::new`, `Control::decode`, `fingerprint`; [`registry/input.rs`](../../crates/controller-input/src/registry/input.rs), `report`, `delta`, `apply_values`, `fault`.

Links are repository-relative. “OS delegated” below means the OS parser may understand a construct; Cockpit neither parses the original item nor proves lossless retention of it.

## Flags, arrays and sample semantics

Windows semantics require particular care: [Microsoft button capability arrays](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/button-capability-arrays) describe preferred aliases and data indices for button-array usages. Filtering alias entries preserves a preferred usage, not the complete alias set. `IsRange` describes a capability usage range; it is not the Array/Variable flag. [HidP_GetData](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/nf-hidpi-hidp_getdata) returns active button indices and scalar value data, but excludes usage-value arrays. Those facts explain why button-array support and usage-value-array support need separate evidence.

| Flag/shape | H0 requirement | Current behavior and coverage limit |
| --- | --- | --- |
| Data / Constant; padding | Retain both flag states and field spans; padding does not become an actionable control. | W consumes caps/data, not constant bit layout. M current model does not expose constant flag. L kernel translation has no padding. C cannot reconstruct discarded constant fields. |
| Variable scalar | Show declared association, width, logical range and raw value; actionability is an explicit separate decision. | C maps Button page, selected Generic Desktop/Simulation axes and Hat; all other usage pairs diagnostic. “Scalar parsed” does not imply “all HID usages supported.” |
| Button array selectors | Preserve slot raw selectors and usage resolution when raw data exists; distinguish slot identity from logical button identity; explicit no-selection/error/rollover diagnostics. | W obtains logical active button data indices through HidP; C implicitly releases missing mapped buttons within that report. This can support logical button state without retaining selector slots/array metadata. Existing fixtures do not establish every selector/rollover case. M arrays diagnostic; L kernel-translated logical key state cannot prove original selector fidelity. |
| Usage-value arrays / repeated count | Preserve count, packed bytes and element addressing; decode only with dedicated supported semantics. | W marks nonrange value ReportCount>1 diagnostic; no `HidP_GetUsageValueArray` call. M count!=1/arrays diagnostic. `HidP_GetData` alone is not array coverage. L original layout absent. |
| Absolute / Relative | Preserve flag; relative samples need explicit delta/event semantics, not retained absolute position. | W relative value caps diagnostic. M relative elements diagnostic. L only EV_KEY/EV_ABS are represented; EV_REL is not mapped. C has no relative flag/sample type. W button caps' IsAbsolute is not checked by `parse_caps`; do not claim all relative controls are safely classified. |
| Null State | Preserve null capability and separate value quality; test null on hats and non-hats, including signed/out-of-range representations. | C `has_null` retained; only Hat out-of-range plus HasNull yields normalized None. Axis/button null outside range errors; there is no general null-valued sample state. M retains HasNull; L synthesizes neutral hat value 8. |
| Wrap | Show flag, retain raw range; wrapping policy cannot be inferred from an axis name. | Not in C; W/M metadata beyond current projection not retained. No wrapping interpretation claim. |
| Linear / Nonlinear | Show declared flag, keep any derived curve explicitly separate. | Not in C; normalization is linear integer scaling for known axes, with no retained nonlinear qualifier. H0 must surface this limitation before claiming semantic fidelity. |
| Preferred / No Preferred State | Inspect flag; do not infer a neutral baseline from it. | Not in C. Current baseline depends on acquired samples; no preferred-state inspection evidence. |
| Volatile / Nonvolatile | Inspect only where meaningful for report type; reserved Input bit stays reserved. | No Output/Feature flag inventory; cannot infer volatility from current input samples. |
| Bit Field / Buffered Bytes | Preserve flag and byte payload/layout; no generic scalar conversion for opaque bytes. | No buffered-byte representation in C; scalar/diagnostic u32 is not full raw byte preservation. |
| Reserved flag bits | Show raw bits and reserved classification; unsupported extension remains visible. | General Main-item bitfield not retained; cannot report unexposed bits as cleared. |
| Repeated usage across reports/collections | Identity includes source/interface, report type/ID, collection/path and physical field/element identity; avoid name-based merge. | W control ID includes page/usage/report/link/data-index. M ID includes page/usage/report/parent/cookie. L evdev IDs use key/axis/hat codes in its source identity. These backend identities are not original raw bit offsets or interchangeable across OSes. |
| Signed and unsigned values | Keep encoded bits, signed interpretation and normalized result separately; widths above supported decoding remain inspectable. | C mapped decode supports 1–32 bits. Diagnostic decode returns unsigned u32 as native and no normalization; that is not sign-aware arbitrary-width raw decoding. M marks >32-bit/invalid-range elements diagnostic but callback values outside supported i32..u32 range cause a gap. |
| Hat direction/neutral | Explicit declared range and null; no guessed center or accepted unsupported direction cardinality. | C normalizes only 4/8 directions; null Hat yields None. L combines paired -1..1 EV_ABS hat axes and synthesizes neutral 8; this is a translated hat model. |

## Reports, transport and evidence by platform

Windows [RAWHID](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawhid) batches have an explicit per-report size and count. The code validates their product before walking reports. Microsoft's [HIDP_VALUE_CAPS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_value_caps) exposes more metadata than `Control` retains, including physical limits, units and flag fields. Do not confuse OS API availability with current Cockpit implementation.

Linux [hidraw documentation](https://www.kernel.org/doc/html/latest/hid/hidraw.html) describes unparsed report reads and descriptor retrieval via `HIDIOCGRDESCSIZE`/`HIDIOCGRDESC`; numbered read reports carry a leading report number, while unnumbered reads start with payload. Those capabilities belong to a possible distinct adapter, not the current evdev implementation. Read/write and feature ioctls in that API do not authorize H0 inspection to send anything.

Apple's [IOHIDElement APIs](https://developer.apple.com/documentation/iokit/iohidelement_h) expose parsed element attributes, including report count/size/ID, units, physical/logical limits and flags. Current M copies only a subset into `Element`. Apple's [IOHIDDeviceGetReport](https://developer.apple.com/documentation/iokit/1588659-iohiddevicegetreport) is synchronous and documented primarily for feature reports because polling input support varies; a successful element callback is not evidence of an original complete raw-report capture.

| Surface | Current evidence | Explicit H0/platform limit and required next evidence |
| --- | --- | --- |
