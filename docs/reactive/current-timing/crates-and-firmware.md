## Unresolved real sampling in this scope

- Companion serial retains 500 ms pre-identification and 1 s ready/status deadlines; supported firmware's status watch reduces full snapshots but the liveness ping and old-firmware status reads remain. `boot_wait` separately retries connect every 250 ms for an explicitly bounded bootloader recovery.
- Linux/macOS qualification capture scans device inventory every 500 ms with a 4 ms pass delay. No native arrival/removal watch replaces that scan in this path.
- The qualification-only visibility child launch retains bounded 10–20 ms checks. The live Windows visibility worker uses report, inventory and policy wakes. Executable paths and unavailable policy notification coverage retain a 250 ms audit.
- The generic device-template firmware samples physical inputs on a 1 ms main-loop cadence. The Pico Debug board runs its USB service loop continuously.
- The virtual-controller refresh path checks child-process exit every 5 ms within separate refresh/reap deadlines; this is bounded lifecycle polling rather than input sampling.

## Scanner omissions found by source review

The call-site snapshot does not enumerate nonblocking timer conditions or all work nested in the captured firmware service calls. In particular, the generic device-template loop has a `last_sample` threshold that calls `board_read_inputs()` at 1 ms; the gateway main loops repeatedly inspect VBUS/USB and service CAN/layout state around the listed `tud_task()` site; and controller capture gates inventory scans with `last.elapsed() >= 500 ms` around the listed 4 ms sleep. These are source-level timer/poll conditions, not additional call-site rows in the 441-site snapshot. The Pico debug firmware also has no throttle beyond its listed `tight_loop_contents()` hint.
