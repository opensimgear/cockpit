# Native profile visibility and enable overrides

`profile_session_visibility::Visibility` composes the existing controller visibility owner, worker and persistent compare-fenced recovery journal. It never opens another input handle or writes HidHide directly. Current visibility qualification gates remain closed; tests do not qualify physical hiding or a broader visibility scope.

`Visibility::stage(plan, snapshot, io)` performs read-only native capture and preflight outside the active coordinator lock. Its private result binds an exact run owner without I/O; no fabricated owner is needed during staging. Hidden selections must resolve through explicit local assignments to one exact live native physical HID instance each, with a current capture baseline. Up to sixteen physical instances share one policy session. Portable `hidden-while-active` intent captures each selected device's explicitly saved local hide policy, including its chosen executable path when applicable. It cannot invent HideAll, unhide external devices or substitute Unix input suppression for HidHide. Existing native preflight checks feature enablement, qualification, exact global-policy representability and recovery conflicts.

`receipts()` returns one native recovery reference before any mutation. It pins the full profile run owner, a fresh visibility-owner UUID, exact physical controller IDs and preparation hash. It contains no Apply policy, executable path or replayable mutation. The native controller service owns the detailed journal.

After acquisition and genuine baselines, `start()` submits the retained preparation once. An ambiguous or failed Start cannot be retried. `poll()` checks exact job and active journal identities; early termination or attention prevents profile delivery. `stop()` cancels the existing owner, then polls its asynchronous restoration and releases that owner only after restoration succeeds. The Host must wait for `Progress::Active` before arming delivery and `Progress::Restored` before considering cleanup complete.

`from_receipts(run, io)` creates cleanup authority for the exact retained owner. It has no preparation and cannot Start. Recovery uses only guarded native Stop/restore; it never rehides devices or replays profile input. The existing journal compares current state with its still-owned expected state before reversing one field at a time. External changes remain preserved as recovery conflicts. Another native visibility owner is never displaced.

The native profile Host captures that receipt before effects, starts visibility only in the journaled Visibility phase, and waits at most three seconds for the exact active worker before Start. Admission cancellation is checked while waiting; virtual output renewal continues. Active health checks the visibility owner before reducer timers or scripts advance. Neutralize and recovery retain cleanup progress across failures and require completed restoration. An uncertain Stop reply is followed by polls; only a fresh exact-owner Active observation permits initiating Stop again. Pending restoration is never repeatedly cancelled. Empty and Visible plans skip optional visibility services entirely.

Ordinary native preflight still rejects another active visibility session. A protected hidden-to-hidden handoff uses a native-only outgoing reference captured from the exact applied coordinator owner. The controller service proves the matching visibility-owner UUID, worker job, journal session, complete non-restoring journal and current applied driver state. Standalone owners, foreign/pending journals, partial mutations and unqualified adapters remain blocked. Read-only proof I/O does not hold the controller mutation admission lock, so outgoing health and Stop remain available. Owner/job/journal state is rechecked after the read; a replacement with an identical driver state cannot reuse the old proof.

The incoming plan is built against the outgoing journal's captured `before` state. Its one-use native preparation pins that proof; final Host capture compares the exact outgoing profile owner and receipt and validates only its current native worker/journal metadata before transition intent or neutralization. This final check opens no driver and makes no claim of a new driver sample; the prepared actual-state snapshot was obtained off-lock. The ordinary durable transition then revokes outgoing effects and fully restores its journal to the captured original before incoming hiding can start. If the actual driver changed after preparation but metadata has not observed it yet, compare-fenced outgoing restoration fails, preserves that external edit, and prevents incoming hiding. Incoming Start checks the same outgoing session/plan is clean and the driver equals that original, and its own journal also starts there. Unknown hidden state is never treated as original state. A crash retains the existing outgoing/incoming recovery references; recovery only restores those journals and cannot rehide or replay the preparation. All existing platform qualification gates remain unchanged.

Temporary controller publication intent uses the separate native publication
actor behind `profile_session_overrides`. Compatible STM32 CAN gateways must
advertise the exact nonpersistent ownership capability; the adapter seals its
physical targets before claiming and checks private ownership, fresh baselines
and compare-if-unchanged restoration. Existing CAN Enable/Disable remains a
permanent remembered-controller operation and is never used to implement this
intent. Direct USB and Pico publication overrides remain unsupported. See
[publication composition and recovery](profile-publication.md). Hiding through
HidHide remains a separate policy with its existing qualification gates.
