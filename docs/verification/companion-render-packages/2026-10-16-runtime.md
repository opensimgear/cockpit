# Downloadable companion scenes: implementation and hardware record

This record extends the [foundation checkpoint](2026-10-16-foundation.md) and the [complete plan](../../companion-render-packages.md). GitHub tracks [R2](https://github.com/opensimgear/cockpit/issues/72), [R3](https://github.com/opensimgear/cockpit/issues/73) and [physical qualification R6](https://github.com/opensimgear/cockpit/issues/76). Implementation is in draft [PR #77](https://github.com/opensimgear/cockpit/pull/77).

Both boards have reached live operation with independently compiled A and B packages, and both full application hashes now match their installation readbacks afterward. The corrected Waveshare repeat completed without unintended disarms. Physical touch/visual confirmation remains in progress. Package C adds held-button animation through the existing renderer ABI but exposed a Waveshare runtime failure; package D confines that animation to thin bands and has passed the native gates. D's hardware run is still in progress. These results establish the downloadable rendering path, not completed R6 qualification.

## Implemented path

The pure TypeScript compiler lowers a native validated source publication and resolved visual recipe into an exact canonical manifest plus OSGC semantics, OSGS scene, OSGI image and OSGF font objects. The original A/B starter panels are independent compositions for each screen. B adds a composite and different artwork/bindings without adding a firmware widget type. Bundled Rajdhani fonts carry their OFL license; Python font preparation is a development step.

The native host compares every compiled semantic control/output with the trusted source. An authenticated device negotiates its exact profile hash, prepares an assigned package and reads at most 2,048 decoded bytes at a time. Preparation creates no input source. The device streams to inactive raw flash, verifies all hashes, canonical metadata, binary structure, references and resource bounds, then commits its journal marker last. Offline boot restores verified content, never an armed state. Host disk selections are also restored only after source revalidation; eviction protects active and prepared packages.

After successful presentation, `render-open` rechecks source/package/profile/descriptor identities and creates a fresh disarmed session. Existing neutral baseline, source ownership and hard input leases remain in force. Normal traffic uses bounded compact typed feedback, not graphics or layout commands. USB and real pinned WSS tests exercise the same host management boundary. Main renders eight tiles per slice; touch sees an immutable hit cache published after the display fence. Navigation stops input and obtains a new session.

The initial native adapter supports momentary controls, navigation and boolean/numeric outputs. Its logical shim permits 32 total controls plus outputs. Numeric source endpoints must be exactly representable in Q16.16; 0.1–0.9 is rejected explicitly, while 0.5–99.5 is supported. Arbitrary text feedback, complex input/XY/triangle controls and designer UI publication are subsequent qualification/integration work. Widgets are qualified per profile; compatibility across all screens is not required.

## First physical Waveshare run

The engine installer wrote only bootloader/table/application at offsets `0`, `0x8000`, `0x10000`. It validated the existing partition table and security state first, verified all three written ranges with SHA-256 readback, and checked NVS/PHY integrity on-device before and after. No raw NVS backup or eFuse write was made.

Both A and B reached `live-armed` through the production USB manager, with host-accepted synthetic numeric/indicator feedback. Input source loss occurred on assignment replacement before the second package download. A read-only full application readback after A → B matched the installation exactly:

`006a5f180476b37a543108b3106c3bd23fa278efa99f2a36e70c5d1993bafef6` (942,448 bytes).

This establishes the unchanged-firmware package swap for that run. It does not establish a stable soak. B later lost its connection; the initial log omitted the existing device fault-status field, so the exact physical cause cannot be asserted from that trace. The run also exposed a deterministic same-package warm-presentation bug: a replaced logical shim with unchanged scene pixels did not trigger the new readiness fence. A regression-tested fix now presents trusted chrome once for that activation without redrawing valid scene pixels.

A separate deterministic UART ownership defect was found during investigation: the outer command parser could retain a prefix at EOF and then let the synchronous reply parser consume its suffix. The fix retains parser ownership until newline; an armed fragment stalled for 100 ms cancels input without renewing its ACK lease, and poisoned suffixes are discarded until newline. Native fragmented/timeout/held-source regressions pass. The defect is consistent with the initial immediate disconnect, but the old physical log cannot prove that cause. The corrected engine is being checked on both boards before stable results are recorded.

### UART follow-up

Firmware `2026.10.17.1` lowers the UART receive FIFO trigger from 120 to 64 bytes. At 921,600 baud this increases hardware headroom from approximately 87 to 694 µs. It adds a 16-entry driver event queue and thirteen saturating uint32 diagnostics for UART and request-parser failures. Polls drain at most sixteen events without waiting; no additional task or custom ISR is introduced. The target's queue control is 84 bytes and each event is 12 bytes. A conservative 400-byte accounting, including counter state and allocator allowance, fits the dedicated 512-byte reserve. The total auxiliary allowance rises from 1,536 to 2,048 bytes while remaining within each profile's renderer ceiling.

Fixed fault statuses distinguish transport failure, explicit host rejection, malformed source ACK and failed input-health monitoring. Public status allows 2,048 bytes and has a regression with maximum legal escaped names, SSIDs, identities and counters. Native serial coverage is 100% lines / 95% branches; synchronous serial parser coverage is 100% / 75%; client coverage is 96.57% / 74.92%. Both engine client layouts also pass their gates.

This build changes receive behavior as well as adding observations. Its counters cannot retrospectively prove the older failures' cause. Driver events can be dropped when the event queue is full, so zero hardware error counters alone do not establish a clean UART. Startup wrong-baud probing and interrupted assignment setup are recorded before live operation; live counter increments must be measured separately.

The corrected 420-second Waveshare A/B run completed with two neutral baselines and exactly two source losses: the controlled A/B assignment change and controlled shutdown. A entered live at 82.549 seconds; B at 174.698 seconds and stayed live through the final sample at 419 seconds. Its longest continuously sampled live interval is 244.024 seconds. Across 259 consecutive same-package/session live pairs, content bytes and requests have zero increments, and all thirteen serial-health counters have zero increments with no missing or regressed pairs. Startup/steady ACK maxima are 401/396 bytes. This is a successful short repeat, not the planned 30-minute soak.

The [corrected repeat proof](2026-10-17-waveshare-repeat-proof.json) verifies identical before/after application SHA-256 `7c2f001308152675aef70c5e5676635deb0ce6aeeb7656b1b5f3ff0c818cd263` over 944,352 bytes, with no firmware writes during the A/B runner or final read-only verification. NVS/PHY checks also match. Initial wrong-baud/setup observations remain explicitly separate: 101 break events, six full-queue observations and one request timeout before first live operation.

Stopped diagnostics over 464.525 seconds since boot measured minimum internal heap 73,207 bytes, smallest largest block 47,104 bytes and main/touch/network stack headroom 4,336/6,960/5,412 bytes. Sampled active touch/render/source-ACK age maxima were 22/386/313 ms. Successful source ACK latency peaked at 22 ms; the longest display fence was 148.851 ms. Four cumulative host request failures are present in a window that also spans setup, assignment replacement and stopping; that cumulative counter does not attribute individual failures. The device-event and source-loss records establish that this repeat had no unintended live disconnect. No physical input edge or game output was recorded.

### Downloaded button animation

The user reported no button animation. A/B author static pressed highlights, while their sole timeline animates a stale telemetry lamp. Package C retains B's composition and adds repeating step-color timelines to the two existing pressed masks. It uses three timeline slots, with unchanged dirty-pixel, layer and blend budgets; Sunton allows four slots. All existing A/B files and profile hashes remain byte-identical. Both buttons have bright/dim/repeat/release golden frames, and both native engines admit C and verify held animation and cached restoration.

The physical C run captured two unintended Waveshare input cancellations at approximately 288 and 338 seconds; Sunton remained stable in that run. Stopped Waveshare diagnostics recorded a maximum active render age of 602 ms, above the 600 ms input-health limit, with zero steady UART-counter increments. The cumulative touch-failure count was 19, and the reported fault was generic. These observations establish an unhealthy C run; they do not attribute both cancellations solely to rendering or exclude other touch/input-health failures.

The renderer compares animated properties even when their nodes are hidden, so C's two full pressed masks cause periodic repaint work while neither button is pressed. Native tests with unchanged feedback and unpressed buttons measure 12 tiles (6,144 pixels) on Sunton and 52 tiles (26,624 pixels) on Waveshare at the color step, despite byte-identical displayed pixels. This is a bounded runtime cost, but it consumes the same render-health window as visible work.

Package D preserves C's full static pressed glow and adds one small pressed-visible rectangle per button. Only these bands receive the existing 800 ms repeat step-color timelines: 32 × 2 pixels on Sunton and 120 × 3 on Waveshare. Compiled tile coverage and actual native tile writes agree at two Sunton tiles (1,024 pixels) and four Waveshare tiles (2,048 pixels), reducing periodic damage by 6× and 13× respectively. D adds two nodes and two bindings, uses three timeline slots, and retains the existing worst-case dirty union: 15,872 pixels on Sunton and 71,168 on Waveshare. Both use at most seven blend layers, within their profile limits.

D introduces no firmware or renderer-ABI change. Its semantics, images and fonts match C, while its source/scene/manifest identities identify the revised composition. All 128 pre-existing A/B/C files remain byte-identical. The automated gates now cover 28 renderer tests, 80 exact C/TypeScript golden frames and 18 proof-report tests. Both native engines admit D and verify held bright/dim/repeat states, release, hit-cache readiness and warm restoration. The C → D hardware run is ongoing; no D physical stability or touch result is claimed here. The full application hash checks for both earlier A/B runs remain verified as recorded above.

The pulse runs while connected, armed and held, on the existing page/connect clock. Stopped screens freeze their clocks and disable input. A quick DOWN/UP can also be visually coalesced while a previous scene frame is pending, although input edges are queued separately. C and D demonstrate held animation in the automated renderers; physical touch confirmation remains pending, and a bounded visual press latch or event-relative animation remains R5 work in [#75](https://github.com/opensimgear/cockpit/issues/75), with control-input semantics kept separate.

The bench supports `--revision B --switch-to C --switch-after 15` and the package-only follow-up `--revision C --switch-to D --switch-after 15`. Optional `--stop-file PATH` ends the demo through normal source/port shutdown when that new file appears; existing stop paths reject before the bench starts. These animation demos send packages and typed feedback through the same production Hub/USB path, with no firmware installer involved.

At head `82ed4cb`, the [complete companion firmware workflow](https://github.com/opensimgear/cockpit/actions/runs/38975412347) passes: portable firmware tests, host-wire tests, generic ESP32/S3 builds and both real board builds. At the earlier `8cb05fa` checkpoint, frontend checks also pass. The broader PR is not green: native controller jobs stop on the existing mapping-host lockfile mismatch; Android cannot install `platforms;android-37`; iOS simulator's child pnpm install aborts without a TTY. Those jobs do not reach a companion renderer failure and are tracked separately from this physical proof.
