# Profile list and native activation progress

The profile list refreshes every three seconds while visible and immediately on window focus or visibility changes. Passive refresh preserves dirty editor drafts and ignores overlapping reads. The redundant Refresh button and global discovered-component count are removed. Import profile appears immediately before Add profile.

Manual activation receives a fresh operation UUID. Independent native progress and cancellation commands bypass the profile admission/coordinator locks. Cancellation revokes only that operation's captured admission epoch; a stale cancellation cannot deactivate a later owner. Read-only preparation cancellation preserves the previous owner. Cancellation after takeover waits for the existing compensation path and reports whether recovery is required. If activation commits before cancellation takes effect, the UI reports that the profile became active.

The native Cockpit opens an owned, nonmodal, undecorated 600 × 76 Tauri window. It contains only current status text and a Cancel button on the right. An application-wide presenter manages this window independently of the Profiles page, including automatic activation, game launch and application of saved active-profile/panel changes. The child window has no gateway permission; Cancel and Escape submit the displayed operation's exact identity through its parent. The window stays visible until activation or cancellation cleanup settles. Native-window failure falls back to a compact in-page dialog.

The native host reports work immediately before the actual operation: validation, releasing the previous profile, hardware configuration, input acquisition, virtual-device creation, companion panel assignment/cache/download/rendering, fresh input baselines, device hiding, mappings, keyboard/mouse binding activation and route startup. Branches without the corresponding resource do not announce it. Companion download byte counts supplement the current companion step only; they cannot obscure later mappings, visibility or game work. A bounded per-operation step history supports verification without adding delays merely to display fast steps.

Automatic selection and explicit game launch use the same tracker. A hardware-first game launch keeps its operation ID while rebinding its native admission epoch, then reports Launching followed by the actual game name, process startup/verification and game-context binding. Exact cancellation remains valid through that epoch transition. Observing an externally started game activates its profile without falsely announcing another launch. Cancelling saved application preserves the durable saved document and follows the normal previous-owner/compensation rules.

The current-operation query and exact cancellation bypass both native admission locks and blocked JavaScript library queues. The application has one presenter, so navigating to Overview or opening Debug does not create or dispose a second progress-window owner.

Native window commands fence stale updates, cancellation and close requests by operation identity. Adapter tests cover browser timer receivers, failed creation/update cleanup, cancellation retry and stale callbacks. The Debug view shares the runtime controller without creating a second progress-window owner.

## Physical acceptance

`node --test tests/ui/profile-activation-progress-native.mjs` passed in 38.9 seconds against the actual dev Cockpit, its native child window and the paired Sunton USB screen on firmware `2026.10.20.1`. No IPC or companion was mocked. Evidence and screenshots are in `.research/profile-activation-progress-native/`.

The list observed externally created/deleted profiles automatically, and the actual toolbar placed the icon-bearing Import action immediately left of Add. The native window displayed the exact companion's cold image download. The test verified its compact viewport, only text/button contents, right-aligned Cancel and absence of overflow, heading, progress bar or footer. After navigating to Overview, the same window's byte count advanced from `0 / 78 KiB` to `2 / 78 KiB`. Clicking its actual Cancel button reached the exact backend operation; cancellation completed in 226 ms. This cancellation occurred after takeover began, so the native coordinator correctly required recovery. Returning to Profiles displayed a single friendly cancellation message with Recover at the right, and the actual Recover button performed cleanup.

After explicit recovery, a new activation UUID retried successfully. The physical screen downloaded all 79,200 raster bytes with one cache miss, reached ready with a fresh session and neutral baseline, and became owned by the profile. The progress window closed. Deactivation restored the original panel and the final native status had no owner and no fault. Temporary profiles and panel publications were removed.

On the final binary, `node --test tests/ui/panel-save-active-profile-native.mjs` passed in 10.26 seconds. UI Save updated the active profile's physical panel in 3.154 seconds with a fresh session and neutral baseline, one image-cache hit and zero misses. The actual rendered title and button text matched the saved changes. Deactivation restored the original panel, temporary data was removed, and final status had no owner or fault. This exercises the saved-application path now wrapped by the same native progress tracker; tracker/cancellation behavior is additionally covered by the native save tests.

During qualification, a prior failed input acknowledgement left the physical companion unarmed. A subsequent activation correctly rejected that missing verified route during preflight. Native stack sampling and independent status requests found no new tracker deadlock; an intermittently unresponsive CDP HTTP endpoint affected the diagnostic client separately. Restarting the dev Cockpit restored a fresh ready companion session without an explicit reconnect. The final run started from that verified baseline.

The hardware run used the actual profile/companion stores with only game setup temporarily isolated through the existing `OSG_GAMES_CONFIG` override, avoiding the previously documented ACR executable hashing overhead. Persistent game setup was not changed. The ordinary dev launch was restored afterward; its actual native status had no owner or fault, and the Sunton had its original unowned panel ready and armed with a fresh matching session.
