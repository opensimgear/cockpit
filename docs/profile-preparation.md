# Native preparation and delivery

`Registry::prepare_port(resource, observedPort, exactContractHash, access)` selects one current, unambiguous provider route and returns a native-only `PortPreparation`. Its private pin includes inventory session, resource/capability generation, provider scope/key/session, exact route and contract. It has no serialization or conversion to `ResourceToken`. `validate_preparation` rejects changed identity, connection, catalogue, route or generation.

Read preparation can wait for a baseline; it cannot deliver a known value. Hardware outputs keep existing write/conflict gates. A game-integration pin can describe a provider still needing acquisition, but the native game adapter must independently verify the candidate game process and exact setup/catalogue revisions. A pin never authorizes a simulator command or bypasses the native applied owner.

`compiler::compile_for_preparation(document, snapshot, pins)` validates the full typed graph using these native pins. Plan source/sink preparation fields are omitted from JSON and delivery tokens remain absent. It preserves all structural, storage, backend, layout, visibility, companion revision and route conflict checks; absent or nonmatching game context stays dormant. It does not reinterpret arbitrary blocked diagnostics as readiness. Its portable program hash agrees with a later delivery compilation; its capture fingerprint also pins acquisition metadata.

The native inventory `snapshot_for_preparation` captures the compile snapshot and selected pins under one cached lock. `validate_delivery` rechecks the actual `ResourceToken` against the cached registry and returns its exact route. Neither method invokes discovery or changes a baseline flag. `refresh_native` is an explicit coordinator capture operation; background and deliberate refreshes serialize collection/adoption with one monotonic revision source.

After acknowledged provider acquisition, the coordinator refreshes actual provider state and recompiles normally with fresh delivery tokens. A pending baseline, stale token, changed boot/configuration or failed provider cannot supply data or receive effects. The coordinator must compare the prepared and delivery program identities and enforce subsystem-specific acquisition receipts before delivery. Optional offline and dormant game branches remain distinct from required setup failures.
