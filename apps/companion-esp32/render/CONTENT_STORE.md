# Downloadable package content store

`content_store.{h,c}` is an allocation-free NOR-flash store with one 2048-byte transfer/hash scratch buffer. Every incoming chunk is at most 2048 bytes, sequential within its manifest/object; a complete package is never allocated. `begin` copies candidate metadata, `erase_step` erases one sector per call and writes its immutable header last, `write` stages bytes, `verify` hashes every object and the exact manifest, and `commit` writes an alternating journal record with its commit marker last. Input sessions are outside this module and must remain stopped throughout staging/activation.

The first two erase sectors hold alternating 128-byte journal records. The remaining region contains two equal sector-aligned slots, each beginning with a 512-byte explicit little-endian header in its own erase sector. The journal binds generation, slot, exact header SHA-256 and package/manifest SHA-256, with its own SHA-256 and final commit marker. Reserved bytes and all bounds are checked. Sunton slots are 0xFF000 bytes each; Waveshare slots are 0x2FF000, including their header sectors. Package admission also enforces the configured 768 KiB / 2560 KiB caps, not merely physical fit.

SHA callbacks stream through the fixed scratch buffer. Required validation callbacks compare exact manifest bytes against every candidate metadata/object field and independently admit binary contents, references, semantics and profile budgets. Hash checks alone cannot replace those callbacks or host authorization. Neither boot scan nor acquisition creates an input writer. Scan revalidates the committed candidates and selects the greatest valid generation; corrupt/incomplete newer data falls back to the older verified slot or returns diagnostic/no-content. Content restoration never restores armed state.

The caller serializes state transitions. A rendering view acquired before a swap remains pinned to its old immutable slot. The next update cannot erase that slot until its unique owner releases the view. Rendering readers may run during writes to the other slot; callbacks synchronously consume supplied buffers. `osg_content_reader` bridges a pinned view/object to the existing `osg_render_read` decoder callback. Validation callbacks receive a temporary read-capable view, which must not escape the call.

`content_store_esp` opens only the named `ui_store` data/0x40 partition at 0x190000, with the exact known-board size and no encryption. Missing/legacy/mismatched partition tables are rejected without erase/write. It provides ESP-IDF partition operations and mbedTLS SHA-256; credentials and NVS APIs are not used.

The custom CSVs retain standard nvs=0x9000+0x6000 and phy_init=0xf000+0x1000, expand factory app=0x10000+0x180000, and allocate ui_store=0x190000+0x200000 on Sunton or +0x600000 on Waveshare. These end at 0x390000 / 0x790000. This is a one-time engine/table migration: compare the device's actual backed-up table before installation, especially any old partitions beyond the app. Existing build sdkconfigs do not automatically adopt changed defaults; use an explicit fresh configuration and inspect its generated partition table before staging firmware. No whole-chip erase, NVS deletion or hardware write is performed by this module's tests.

From the Cockpit root, run `python3 apps/companion-esp32/test/content_store.py` and `python3 apps/companion-esp32/test/content_store_esp.py`. Native ASan/UBSan tests use actual OpenSSL SHA-256 and inject power loss at every erase/write/hash/validation/journal/commit event, with zero, prefix or complete mutation before failure. The 318 recovery cases return complete old/new content or diagnostic mode, and verify pinned-reader safety and exact 2048-byte I/O bounds. Coverage is 100% lines/functions and 72.44% branches for the store; the SDK-mocked adapter is 100% lines/functions and 85% branches. These are fault models and software evidence; physical power cuts, flash wear behavior and board/transport qualification remain separate tests.
